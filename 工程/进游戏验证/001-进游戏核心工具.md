# 进游戏核心工具（唯一真源）

> **标记权：只有主人能标「核心」。** 原4类由主人2026-11-04标记；2026-11-16主人追加 `rdd-controlled-restart` 为核心驾驶技能，并重申相机核心入口（§4/§8）。核心身份与所属层是两个维度：Harness层不等于不重要。
> AI 可自行在第 6 节登记、验证和维护非核心扩展，无须逐项请示；只有主人可以新增或更改核心标记。

## 1 · 实验台（核心 · 主人 2026-11-04 标记）

实验台把本轮环境、判据、时间线和旧案例组装起来，产生可回查的结论。下表是运行与裁决部件；取证部件及分工见本页第 7 节。

| 件 | 干什么 |
|---|---|
| `bench.js` | 账本：catalog / tip / signal / verdict / queue / health |
| `world-view.js` | 环境台：world_probe → 一份环境文件（不重复逐探针查） |
| `exp-runner.js` | 跑实验：复制母版、起游戏、派目标、复位 |
| `exp-judge / exp-card / exp-*-ab` | 按冻结判据机械裁决 |

- **自维护**：谁跑谁往里加探针、坑、裁定。
- **别被它骗**：它说"通过"，必须能追到原始事件 / 前后差额 / 持续窗口；只有近期日志 = 只是 telemetry。
- 此处不维护当前进度；查所选run和现行施工单，不从旧崩溃快照判断今天。

## 3 · 指令 + MCP（核心 · 主人 2026-11-04 标记）

## 4 · 摄像机（核心 · 主人 2026-11-04 标记）—— 两套是**一个系统**

同一个目的（看见 / 拍下 / 跟住），三种入口；不是三套设备。拍摄先加载核心技能 `rdd-observer-camera`；主人稳定机位是原版 **Possession**（旁观者附身+位置刷新），不是旧 SHOULDER/ORBIT/LOCK rig 或 BODY。正常沿现有配置自动附身，先用 `cam_state` 只读核目标/active/matches，有效就直接录像，不额外改机位/清空重绑/镜头TP；仅失效按该技能异常恢复，其他AI不抢相机。

| 入口 | 是什么 | 什么时候用 |
|---|---|---|
| `mcp__numencam__*` | 外部的手：`cam_photo` 静帧、`cam_rec` 录像、`cam_state` 自检 | 默认；静帧优先，录像按条拍 |
| `/cam ...` | 游戏内命令：`possess / bind / follow / rec` | 要跟住同伴时，`/cam possess <名>` 一条搞定，零刷屏 |
| PrintWindow 截图 | 兜底：`capture-win.ps1 -TitleMatch Minecraft` | 只要一张干净的游戏窗口图 |

## 6 · AI 扩展工具登记栏（非核心）

AI 可以自行补工具、登记、复验或撤回；**本栏每一项都是非核心**，验证有用也不升级。核心标记只由主人决定。先查[工程工具注册表](<本机路径已省略>)和本栏；已有入口能解决问题就补案例或复用。这里记用途和效果，脚本、技能、MCP 的可调用入口仍在各自实际注册处，填表不等于安装或授予权限。

脚本位于 `本机路径已省略。已有条目按本次拿到的证据标记；“待验”不是判定无用。

| 工具 / 入口 | 用途与缺口 | 验证状态与边界 | 最近调通（日期 / 回执） | 最近证实有用（日期 / 真实任务原证） |
|---|---|---|---|---|
| `monitor-report.ps1` | 只读当前日志会漏掉轮转前的事件；合并当前文件和归档，按类型统计。 | **样例已验**：归档计数与缺输入见下例。分组的“bytes”按字符长度估算，不能当精确磁盘字节。 | 2026-11-20，离线样例见下 | 未知 |
| `companion-calls.ps1` | 区分同伴调用与外部 MCP 调用，避免把监控操作算给同伴；含归档。 | **待验**：用同伴和外部各一条已知事件对账。 | 未知 | 未知 |
| `tool-whitelist-check.ps1` | 区分“源码有工具”和“它在白名单内”；基线模式看新增项。 | **待验**：用一个新增漏登和一个已登工具对照。 | 未知 | 未知 |
| `tool-request-check.ps1` | 白名单不能证明模型收到；查实际请求里的工具名。 | **待验**：用已知请求，与原始 tools 列表逐项对照。 | 未知 | 未知 |
| `prompt-check.ps1` | 分辨技能或提示块未送达，还是模型收到了但没用。 | **待验**：用有块、缺块的两份请求核实。 | 未知 | 未知 |
| `toggle-tool-visibility.ps1` | 需要受控修改可见性并能找回原配置；这是写操作。 | **待验**：在隔离配置上核预览无写入、实际增删、备份可恢复。 | 未知 | 未知 |
| *新增：稳定 ID / 入口；登记者、登记日、维护者* | *旧办法哪里不够；读或写什么* | **待验**；*适用范围、版本和判据* | *未知或调用回执* | *未知或任务证据* |

旧条目的登记者、日期或回执无原证就记未知；使用、报错或换版本时顺手补原行。成功调用只更新“最近调通”；有真实任务效果的证据才更新“最近证实有用”。低频或没有近期记录都不是失效证据。

**怎么判有用（只用于这件工具，不是进游戏门禁）：**

1. 登记时先写判据：谁在什么场景要作什么判断；不用它或用旧工具会得到什么结果；什么变化才值得保留。状态从 **待验** 开始。
2. 用已知答案的正例和能暴露误判的反例实际调用，记录输入、版本、命令、预期与实际；对照独立原件，不拿工具自己的输出证明自己。缺日志不算零，退出码 0 不算有用。会改状态的工具在隔离副本验副作用和恢复。
3. 正反例可复跑只标 **样例已验**。要标 **有用（限某场景）**，再给至少一次真实任务的原证：同一输入与旧办法比较，具体纠正了什么判断、减少了多少工作或补到了哪条证据。链接原 run/验证卡，写明日期、版本和适用边界。不用为补标签专门开游戏。
4. 实际与判据相反记 **无效（原因）**；坏了或被取代记 **失效（版本/替代入口）**。证据不够保留待验；版本或数据格式变化，标待复验，维护者按原样例复跑后再更新。确认失效或有可靠替代时，AI 可撤下非核心项的默认推荐；在原行留原因、替代入口及恢复条件，不抹历史、不因冷门删工具，也不据此改变宿主可见性。工程探针已有 `bench.js probe add`，验证卡/裁决沿用原件；这里不另建运行账本。

**实填样例 · 2026-11-20，维护：本次整理 AI。** `monitor-report.ps1`（SHA-256：`FBBAED2B7ED33F40A8378D5E2B2D56C03B355023181DE2E2F135191792CF8872`）。在测试目录的 `config/numen/monitor/` 放两份 JSONL：`内部原始日志未公开` 一行 `{"type":"current"}`，`内部原始日志未公开` 两行 `{"type":"archived"}`。执行 `monitor-report.ps1 -GameDir <测试目录>`：只看当前文件会数到 1 条；预期合计 3 条，其中归档 2 条；实得 `+1 rotated / lines=3 / archived 2 / current 1`。换成无日志目录，实得 `no monitor file`，不能据此报告“0 次”。这是离线样例，不证明该脚本在每个真实 run 都有用。

## 7 · 实验台内部怎样组装证据

第 1 节的实验台用下面这些部件回答同一次实验的不同问题。它们属于实验台的用途与分工；具体调用仍走各自的脚本或 Harness MCP，不是游戏内动作工具，也不因归入实验台而逐个获得核心标记。

| 实验中要回答的问题 | 用哪个部件 | 输出怎么用 |
|---|---|---|
| 当时按什么意图、契约来验？ | `rdd_architecture` | 定位当时的决定、版本和原文，确定预期；设计不能证明实机结果。 |
| 这次实际发生了什么？ | `bench.js timeline <runDir>`、`rdd_timeline` | 前者按本地 run 材料拼时序；后者按运行快照查时间窗、事件和原行。按同一 run、世界、时间窗对账；同一条底层日志经过两个视图仍然只是一份证据。 |
| 以前哪次出现过，可作什么对照？ | `rdd_memory`（当前连接提供时） | 找相似案例并回到旧 run/验证卡；记忆只给线索，不代替本轮观测。 |
| 材料能支持本轮判据吗？ | `bench health`、验证卡与 `exp-judge` | 查覆盖、对照冻结判据，结论回挂原始事件；材料缺失就记未知。 |

例如核睡眠：用契约确定要验“跨夜”还是“绑床”，用时间线查同一窗口的睡眠事件和世界变化，必要时从记忆找以前的误判，再把窗口和结论记入验证卡。不要求每次调齐所有部件。登记、当前会话可见、调用成功、返回了可用证据要分别判断；这里描述组合方式，不声称 `bench.js` 已自动调用全部 MCP。
