#### 0.9.3 五组根因假设及反证

1. **逻辑任务存在与身体当前owner被混用**（#2–7、#17）：多个备货/照顾义务应能保留，但不应因出现就替换主线。已核selector活跃side优先，候选也已有recurring/promptOnly等基础。反证：若该样本根本没激活side却仍偏航，应查规划安装/why分类而非改调度。food379应先接现有真实消费者验收。
2. **看到的事实、当前可用能力和历史完成混用**（#3、#4、#10、#14、#16、#20–21）：asset TTL、完成事实退休、个人spawn分别已有实现，关键是来源、scope、当前准备和失效如何抵达消费者。反证：若当前库存与风险均正确送达而行为仍偏，应查策略选择或控制，而非再添资产表。
3. **动作在飞状态不足以解释进度与风险**（#8–11、#18–19、#23）：现reflex/attack已有控制，仍需查动作意图→实际路径/作用→进度/风险→结果反馈；可能有未加载、未触发、判据欠缺或消费丢失，多因并存。#22通用化与#15性能改造不借此提前。
4. **能力/经验“存在于库”未必进入正确最终请求或被采用**（#1、#6、#13、#24）：planner和executor必须分别验实际正文、可执行能力与当前版本；reason presence、检索数、STABLE和计划改版都不是采用证据。反证：完整送达但工具受阻，应归能力/控制；不能继续改同一提示词。
5. **时间邻近和摘要不等于因果链**（贯穿，#12）：V25观察时间错误、旧ref轮转、core/API发布错层会污染结论。修最窄可查链，不等建设新观测平台再工作。至少一个同scope完整样本足以开始后批，不要求所有UNKNOWN清零。

#### 0.9.4 模块契约、数据流与失败恢复（本轮工程决定）

**复用链路**：当前世界/库存/设施观测 → 原事实与资产投影 → 原主链/recurring/side候选及why → planner/executor按需检索与协商 → 原ActiveTaskSelector选唯一当前任务 → 原Numen调度/ACX run → 实际工具终态与世界后态 → 原条件核验/资产失效/经验复核 → 续主目标。外部timeline/媒体只读投影这条链，不取得目标、身体或资产写权。

- **任务契约**：稳定意图归TaskChain/已有DAILY与SIDE持久源；当前身体焦点仍归原selector/执行槽。先扩现消费者投影多个候选，包含原ID、NodeType、why、已有importance/condition/recurrence、当前状态与due/expiry；缺字段只有被真实消费者证明必要才补optional字段，不引进另一套traits/state/全局优先级。planner只提交/修订候选，执行者可说明选取、延后、取消与证据；服务端核scope后生效。现实现不足以表达多待办时，在现源下扩，而非另存todo库。
- **普通与紧急分开**：食物备货、穿甲、可延期农事是逻辑候选；不改变mainline owner、不耗紧急预算。危险升级由现生存控制转换到抢占，保留被中断ID/代次与恢复条件。选择前查当前有效性；取消须等同一原TaskRecord/AC run明确终态或既有安全交接点，晚回执拒收，不同时驱动身体。不是所有side降成软提示，也不新增逐条人批。
