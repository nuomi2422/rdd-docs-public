## 1. 要解决的问题（带现场证据）

现状：消费者想知道"箱子里的东西变了吗"，只能要么

1. **轮询全量读**（`read` + 定期 `refresh`）——每 10 秒重读一遍整个箱子，绝大部分时候结果没变；
2. **靠 TTL 猜**——2026-11-05 02:41 实机就栽在这上面：箱里已有 5 铁锭，观测因 TTL 仍返回旧快照，
   渲染行一直是 0（039 §22 记了这条）。

根子是**没有"变化"这个概念**：系统只能表达"当前值"，不能表达"变了什么"。

## 2. 定义（写死，不留解释空间）

- **Change（变化记录）**：一次**被存储接受**的观测写入产生一条，含
  `revision`（与观测同一修订号）、`topic`、`key`（观测键规范串）、`kind`、`epochMs`。
- **kind** 只有三种：
  - `CREATED`：该键此前没有任何观测；
  - `UPDATED`：该键已有观测，本次写入被接受且内容/修订更新；
  - `GONE`：该键的观测被显式清除（`clear`/容量淘汰**不算**，淘汰不是世界变化）。
- **游标（cursor）**：一个正整数 = 消费者"已经看到的最大 revision"。**不是偏移量、不是时间戳。**
- **GAP**：请求的 `after` 小于当前保留的最小 revision → 明确返回 `gap=true`，
  **绝不返回空列表冒充"没有变化"**。

## 3. 三条硬规矩

1. **只有被接受的写入才产生变化**。`InMemoryObservationStore.put` 现在会因为"修订号更旧"拒收
   （D-017 那次事故就是它静默拒收），拒收**不产生 Change**——否则消费者会被通知去读一条根本没更新的观测。
2. **GAP 必须显式**。断线/重启/清空导致历史断档时，消费者要的是"你得重新同步"，不是"没变化"。
   这和 039 §4 的四类语义是同一套精神：**读不到 ≠ 空**。
3. **游标只能前进**。消费者拿到的 `nextCursor` 不小于它给的 `after`；空洞由 GAP 表达，不由游标倒退表达。

## 4. 形状（接口草案）

```java
// 核心（world-state-core，纯逻辑）
record Change(long revision, String topic, String key, Kind kind, long epochMs) {}
enum Kind { CREATED, UPDATED, GONE }

interface ChangeLog {
    void append(Change change);                       // 由存储写入路径调用
    ChangesResult after(long cursor, Set<String> topics, int limit);
}

record ChangesResult(List<Change> changes, long nextCursor, boolean gap, long oldestRetainedRevision) {}
```

能力面（`WorldObservationService`）加一个方法：

```java
ChangesResponse changes(long afterRevision, List<String> topics, int limit);
```

## 5. 保留期与容量

- 环形缓冲：**容量上限**（条数）+ **时间窗**（默认 10 分钟），先到先失效。
- `oldestRetainedRevision` 随淘汰推进；`after < oldestRetainedRevision - 1` 即 GAP。
- 为什么两条都留：只有容量，慢变化场景会保留过久；只有时间，快变化场景会挤爆内存。

## 6. 断线 / 重启 / 清空

| 场景 | 行为 |
|---|---|
| 进程重启 | 修订号**从存储最大修订号续号**（039 §27 已修）；ChangeLog 从磁盘或空开始 |
| ChangeLog 落空（新装/清空） | 任何 `after > 0` 的请求都返回 **GAP** —— 消费者被迫重同步 |
| 玩家断线一会儿 | 与进程重启同处理：GAP 或正常续读，取决于保留期 |

**不许**用"重启后 revision 重置"来糊弄——那正是 D-017 的原始 bug。

## 7. 消费者怎么用（伪代码）

```
cursor = 上次保存的游标（可落盘）
loop:
  r = changes(after=cursor, topics=["containers"], limit=64)
  if r.gap:  全量重读一次（read），把 cursor 设为 r.nextCursor
  for c in r.changes: 处理（渲染行/触发判定/记日志）
  cursor = r.nextCursor
```

要点：**GAP 时是一次全量重读，不是"忽略"**；处理完才前进游标。

| `Change.revision` 复用观测修订号 | 观测 revision 是**每个 key** 的版本，不是全局时间线；`goneSeq` 又插进来抢同一个游标 | 拆成两个字段：`ChangeEvent.streamSeq`（日志自己的单调序号，全局唯一）+ `observationRevision`（引用哪版观测，仅供诊断） |
| `kind`: CREATED/UPDATED/GONE | `GONE` 被用在 `clear()` 上，语义是"缓存失效"而不是"世界里没了" | `kind`: `CREATED` / `UPDATED` / `INVALIDATE` / `RESET`；**`GONE` 保留但暂不使用**（等真有"世界删除"语义的 API） |

### 17.2 快照不是历史（对应 R3-1）

- 现行：`load()` 走普通 `put()` → 每次启动都给磁盘里每条观测**伪造一条 CREATED**，历史被污染。
- 提案：`ObservationStore.loadAll(List<Observation>)` 直接填表，**不产生任何 ChangeEvent**；
  - `WorldStateService` 启动时生成 `streamEpoch`（如启动毫秒 + 随机后缀），写进每条事件；
  - 任何 `after(cursor)` 若 cursor 来自旧 epoch → 返回 **`RESET_REQUIRED`**，而不是空列表、也不是 gap 布尔。

### 17.3 全量 + 增量接缝（对应 R3-3）

- 现行：消费者"先读快照、再取游标"，两步之间发生的写入会漏。
- 提案：`read()` 的响应带 `watermark = 当前 streamSeq`；消费者顺序固定为
  1. `read(...)` 拿到快照 + `watermark`；
  2. `changes(after=watermark, ...)`；
  - 中间发生的写入 streamSeq > watermark，必然出现在第 2 步；
  - 若中间发生日志淘汰导致 watermark 已被删 → 第 2 步返回 `RESET_REQUIRED`（可重试一次）。

### 17.4 分页仍要推进（对应 R3-4）

- 现行：`nextCursor = 最后一条**命中**事件的序号`；当本页全被 topic 过滤掉时游标不动 → 消费者卡死。
- 提案：`nextCursor = 最后一条**检查过**的事件的序号`；
  - 未填满页面：推进到"检查完的尾部"；
  - 填满页面：停在最后一条命中处（不越过未处理的匹配项）；
  - 响应增加 `hasMore`。

### 17.5 GAP 的恢复终点（对应 R3-5）

- 提案状态机（消费者侧）：
  - `RESET_REQUIRED` → 执行**一次**有界重同步（一次 `read` + 一次 `changes`）；
  - 重同步失败 → 指数退避（1s/2s/4s… 上限 30s），**不是每 tick 重试**；
  - 重同步成功 → 记 `cursor = watermark`，清除标志；
  - 日志为空且有游标 → 同样 `RESET_REQUIRED`，不是"没变化"。

### 17.6 缓存失效 ≠ 世界消失（对应 R3-6）

- `clear()` / 容量淘汰 → 发 **`INVALIDATE`**（含义：这条观测不再可信，别当成世界变化）；
- 真实的"世界里没了"暂不表达；`GONE` 保留但**不产生**；
- 枚举语义变更必须**版本化**（`ChangesResponse.schemaVersion = 2`），旧消费者读到未知 kind 时按"未知即失效"处理，不许静默忽略。

### 17.7 确定性反例清单（离线，可控时钟）

1. `loadAll` 2 条 → `changes` 为空（不伪造历史）
2. LRU 顺序 `[B2, A1]` + 重启 + `limit=1` → 分页推进正确（`nextCursor` 前进、`hasMore` 正确）
3. 正游标 + 空日志 → `RESET_REQUIRED`（**不是**空列表）
4. 仅无关 topic 持续写入 → 游标仍前进（不卡死）
5. 分页夹缝：第 1 页填满后、取第 2 页前插入新事件 → 不丢
6. `clear()` 后 → `INVALIDATE`；随后 refresh → `CREATED`/`UPDATED`
7. 重复/乱序/同 revision 写入 → 拒收且不产生事件
8. epoch 切换（重启）→ 旧游标 `RESET_REQUIRED`
9. 保留期到期（可控时钟推进，不 sleep）→ `RESET_REQUIRED`

### 17.8 现场验收（R3 要求，沿用）

- 容器**真实放取**触发（不是"无箱子 118 秒"冒充）；
- 静止时不无谓加速（扫频率/tick 耗时记录）；
- 断档重同步**只执行一次**；
- 重启后连续变化；
- 回退路径：保留轮询的有界扫描，关闭有缺陷的增量消费，不丢业务事实。

### 17.9 与现行代码的差距（诚实清单）

| 现行实现 | 是否满足 |
|---|---|
| `Change.revision` 复用观测修订号 | ❌ 违反 R3-2 |
| `wrapSeq`/独立 `goneSeq` | ❌ 违反 R3-2、R3-6 |
| `load()` 走 put 产生 CREATED | ❌ 违反 R3-1 |
| `after()` 过滤后不推进游标 | ❌ 违反 R3-4 |
| 无 `streamEpoch`、无 `RESET_REQUIRED` | ❌ 违反 R3-1、R3-5 |
| 消费者 gap → 重扫一次 | ⚠️ 部分满足 R3-5（缺退避与只一次保证） |

**结论：v1 实现保留作为"能被证伪的原型"，v2 按本文重写；在 v2 通过离线反例前，041 不新增消费者。**

### 18.1 水位采集时机（对应洞 1）

原 §17.3 只说「read 带 watermark」，**没说什么时候取**。没在同一时序里，「中间写入必然出现在第 2 步」不成立。

### 18.2 RESET 活锁（对应洞 2）

原 §17.5 的「RESET → 重同步 → 又 RESET」会活锁。补：

- 转为有界轮询（2 秒一次全量 read）+ 发 `changes_livelock` 告警事件；

### 18.3 schemaVersion 服务端分流（对应洞 3）

原 §17.6 说「旧消费者读到未知 kind 按失效处理」——那是**要求别人自觉**，部署出去的老代码不会自觉。

改成服务端分流：
- 请求带 `schemaVersion`（缺省=1）；
- `schemaVersion=1` → 仍返回旧语义（`GONE`），行为不变；
- `schemaVersion=2` → 返回 `INVALIDATE`/`RESET` 新语义；
- 服务端不认识的值 → 明确 ERROR，不静默降级。

### 18.4 接缝反例（对应洞 4）

§17.7 第 5 条只是「分页夹缝」。补两条真接缝：

## 22. 第四轮审后修正（2026-11-05 08:20–08:45）：loadAll 又打架了 + 消费者状态机

### 22.1 C：loadAll 的淘汰会发 INVALIDATE，和「载入不产生事件」直接打架

### 22.2 消费者侧状态机（042 R3-5 的离线部分）

新增 `ChangeCursorState`（纯逻辑，可在无 MC 环境测）：

| 行为 | 断言 |
|---|---|
| 正常页推进游标 | `cursor=nextCursor`，退避与计数清零 |
| 空页不算失败 | 不累计退避 |
| RESET → 跟到 watermark + 退避 1s→2s→… | 不会原地打转 |
| 连续 3 次 RESET → `livelocked()` | 调用方必须转有界轮询（防活锁） |
| 读到真变化 → 熔断解除 | 「连续失败」才熔断 |
| epoch 切换 → 按 RESET | 首次使用只采纳、不重置 |

11 例，全绿。

### 22.3 D-020 的离线替身

审计指出「用日志出现来证明 D-020」是弱证据（只证明变化到了，不证明重扫被触发）。

- 没变化 → `false`（保持轮询节奏）

## 23. 第五轮审后修正（2026-11-05 08:50–09:05）：D 误报熔断、E 语义重叠

### 23.1 D：正常重启三次就熔断（审计实测）

探针（`maxResets=3`，连续四次正常 epoch 切换）：resets 0→1→2→3，第四次就 `livelocked=TRUE`。

**这是纯误报**：RDD 一天重启十几次是常态，容器可能一整天没变化 → 三次重启后消费者就停自动重同步、发告警。

修法：**epoch 变化是「新流」，不是失败**——立刻重同步、退避清零、不计入熔断计数；
失败计数只统计**同一 epoch 内**的连续 RESET。

两条断言：

- `epochChangeTriggersResyncButIsNotAFailure`：换流 → 重同步、`resets=0`、`backoff=0`、不熔断；
- `repeatedNormalRestartsNeverTripLivelock`：连续 8 次正常重启 → 仍然不熔断。

### 23.2 E：`onPage` 与 `shouldRescan` 语义重叠

两者在 RESET 页上都返回 true，调用方若写 `if (onPage(p) || shouldRescan(p))` 会双重触发。契约写死：

- `ChangeCursorState.onPage` 管**游标 + 退避 + 熔断**；
- `ChangeSignals.shouldRescan` 只回答「要不要立刻重扫」；

## 24. R3 接线方案（提案，2026-11-05 09:35）

> v2 的类和测试都在了（§19/§22），缺的是"怎么接到生产路径上而不打断 v1 消费者"。
> 本文只写方案，**不改代码**。

### 24.1 现状

`WorldStateService` 持有：

- `InMemoryChangeLog changeLog`（v1，语义 = 观测 revision）
- `InMemoryObservationStore store`（写入时发 v1 事件）

能力面 `WorldObservationService.changes(after, topics, limit)` 直接吃这个 v1 日志。

### 24.2 目标状态（R3 完成后）

| 层 | v1 | v2 |
|---|---|---|
| 存储 | 保留兼容 | `ObservableStoreV2`（streamSeq/epoch/INVALIDATE） |
| 日志 | 继续可读 | `InMemoryChangeFeed` |
| 能力面 | `changes()` 默认仍是 v1 | 新增版本化入口，只有显式 v2 才走新语义 |

### 24.3 关键决定：能力面怎么带版本

现在 `changes(long after, List<String> topics, int limit)` 没有版本参数。三条路：

| 方案 | 做法 | 代价 |
|---|---|---|
| A（推荐） | 新增 `changes(ChangesQuery q)` 重载，`q.schemaVersion` 缺省 1 | 接口变大；v1 行为逐字不变 |
| B | 给 Request 加字段 | Request 是"读请求"，塞增量参数不伦不类 |
| C | 靠服务端配置全局切 v2 | 消费者无法逐个迁移，回滚要重启 |

推荐 A：**版本由调用方声明**，服务端按版本分流；不认识的值明确 ERROR（不静默降级）。

### 24.4 过渡期双写

`ObservableStoreV2` 上线后，写入路径需要同时：

1. 写 v2 feed（streamSeq/epoch）；
2. 继续写 v1 ChangeLog（否则老消费者看不到变化）。

双写的风险：**两份序号不一致**。约定：v1 只是兼容层，**不保证与 v2 序号对应**；
任何需要跨版本的迁移都走 RESET（v2 语义），不试图对齐两份序号。

### 24.5 接线步骤（每步可回滚）

1. `WorldStateService` 增加 v2 feed + `ObservableStoreV2`（**先不接任何调用点**）；
2. 写入路径双写（v1 + v2），跑一轮离线测试：v1 消费者行为逐字不变；
3. 加 `changes(ChangesQuery)` 重载，`schemaVersion=1` 时转调旧路径；
4. 让 `RddContainerMemory` 显式用 v2（它已经能处理 gap/未知）；
5. 观察一版：v2 消费者无 RESET 风暴、v1 消费者不变；
6. 收口：v1 路径标注"兼容"，文档记录切换时间。

### 24.6 回滚

- 每步只改 `WorldStateService` 一处，回滚即恢复上一个构造；
- 数据层：v2 feed 在内存，回滚不涉及磁盘格式；
- 消费者：`RddContainerMemory` 回滚只需改回 `schemaVersion=1`（**不删新代码**，否则下次还得重写）。

### 24.7 待审的三个问题

1. **能力面重载**用 A 方案可以吗？（`ChangesQuery` 含 schemaVersion/after/epoch/topics/limit）
2. **双写期间 v1 序号与 v2 序号不一致**，你接受"不保证对应、迁移走 RESET"吗？
3. `RddContainerMemory` 切 v2 后，**旧游标（v1 revision）会立刻收到 RESET** —— 首次切换必然触发一次全量重读。这个一次性成本你接受吗？

### 26.18 真实采样频率 1 Hz，不是 4 Hz——SAMPLE_INTERVAL_TICKS=5 目前空转（2026-11-05 10:12）

新版计时日志（按同伴、实测间隔）：

```
[rdd-danger] tick采样 n=200 skipped=0 平均=29us 最大=245us 成功间隔≈19tick 尝试间隔≈19tick 窗口=3980tick
```

**19.9 tick/次 ≈ 1 次/秒**，而配置是每 5 tick 一次（应≈4 次/秒）。原因在调用方：

- RddDetector.onServerTick 先过 TICKS_PER_CHECK = 20 的心跳闸（RddDetector:50/150）；
- 于是 sampleOnTick 每秒才被调用一次，SAMPLE_INTERVAL_TICKS=5 永远满足。

结论：

1. **有效频率由 detector 心跳决定**，不是由 SAMPLE_INTERVAL_TICKS 决定——该常量目前只在 detector 心跳变快时才有意义；
2. 代价：29us/次 × 1 Hz ≈ 每秒 0.03 毫秒，可忽略；
3. 这也解释了早先 间隔=5tick 与墙钟 261s/50s 的矛盾：那个数既不是常量也不是实测。

**§26.9 口径更新**：R2 条件 4 实测值是 **1 Hz、平均 29us、最大 245us**（原写 每 5 tick，应改为 受 detector 心跳限制，约 1 次/秒）。

### 28.4 去重定论：POJO 字段没被剥（2026-11-05 11:50）

根因（审计定位，实机验证）：

- `RddAssetContext.worldAssets(...)` 返回 **List<AssetEntry>（POJO）**，不是 Map；
- 旧 `stripVolatile` 只在 **Map 的 key** 上剥 `observationId/observedAt`，POJO 字段走 `return value` 原样返回；
- 于是两个时间戳进了签名 → 每拍都变 → 去重永不命中。

这解释了三个看似矛盾的观察：落盘 JSON 规范化后相同（对比方在 JSON 层剥了）、
Java 签名每拍不同（只剥了 Map key）、长度恒 76626（结构没变，只是两个数在跳）。

**修法：在 JSON 树上剥，不在对象图上剥。**

`signature(value) = canonical(GSON.toJsonTree(value))`：对象按 key 排序并跳过易变字段，数组递归后按字符串排序。
类型无关（Map/POJO/record/数组一视同仁），剥的就是"要写出去的那份内容"。

**实机验证（rdd 8BF8EB64，11:48）**：

- build stamp 命中：`[rdd-monitor] build=2026-11-05Tjson-tree-signature`（确认跑的是新 jar）；
- asset_snapshot 在 2.7 分钟内 **+1**（此前同窗口 +4~6）；

### 39.1 ContainerMemory 的一处可疑缺口：旧缓存没有时间标记

## 40. 能力/知识缺口实测：goto 的「block + 坐标」自相矛盾（2026-11-05 14:15）

### 根因不是模型笨，是描述自相矛盾

`MoveToTool.description()` 原文（修前）：

> block — … Easiest to reach is not always closest in a straight line, so it may not be the first block
> scan_blocks listed — **give coordinates when it has to be a specific one**.

模型把它读成「block + 坐标 = 指定那一个」，而参数校验（`MoveToTaskRecord.resolveKind`）明确拒绝这种组合。
**描述在邀请它做一件工具不允许的事。**

### 修法（a9c5f0665 之后）

改成：

> When it has to be a SPECIFIC one, **drop block and send that block's coordinates instead**
> (x+z to walk to its column, or x+y+z to stand in the cell) — block and coordinates cannot be sent together.

**回归判据**：同类 `invalid arguments: block means` 的回执条数应显著下降（当前 220 次）。
这条只能靠实机跑一段时间看，不靠读代码。

> 这正是本轮目标要的「知识漏洞」：**工具会拒绝的写法，描述里不该出现**。
