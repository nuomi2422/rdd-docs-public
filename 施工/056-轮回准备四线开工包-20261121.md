## 1. 四条线共用的五条硬规矩

1. **五个身份不许互代**：世界、服务端会话、同伴、代次、run 或调用。日志里对得上，不代表是同一身份。
2. **未知分三态**：没匹配、没覆盖、已过期。三态都不等于 0。
3. **"完成"必须落到实际读端**：入队≠送达，受理≠执行，SUCCESS≠世界目标完成。
4. **共享文件只有一个写入方**（见 §6）。同一注册表/发布入口由主工合，其他人交消费测试。
5. **先红后绿**：每条线先写一个能区分改前改后的判据，再动代码。

## 37. AC 续跑缺陷嫌疑：取消后 resume 重放已成功子步骤（2026-11-22 06:3x，阻塞合入）

- **最小复现（三号，预演树未提交桩）**：`farm_maintain_loop v3`，fake farm 依次返回 `harvested=1`、`0`；第一次调用**成功返回前**触发 `runner.cancel`，同轮 `PAUSED host_cancelled`、`farms=1`；`resume` 后 `SUCCESS`，但累计 **`farms=3`（断言期望 2）**。原 XML：`[内部路径已省略]`。
- **源码嫌疑（三号定位）**：`AcxRunner` 在 child success 之后**先检查 cancel 并立即 return**，而「游标/输出保存」在 return 之后的代码里；因此被取消时**已成功的子步骤没有被记账**，resume 会把这一步再跑一遍。
- **口径纠正（2026-11-22 06:3x，三号/独立审）**：`farms=3` 是**包装器 `execute` 次数**，不等于真实 `farmPort` 派发次数。`PortToolAdapter` 缓存了同步成功回执，resume 可能**先重入包装器命中旧账**，下一轮才真正派发；fake 只有 1/0 两条，所以「重复执行真实动作」**尚未证实**。
- **为什么仍要拦住**：如果重入后**真的**再派发一次，对 `craft/place/attack` 这类幂等性不成立的动作就是重复消耗/重复伤害；所以在这条没分清楚前，AC **仍不能合入、不能实机验收**（但也不把「已证重放」写进结论）。
- **代码线索（2026-11-22 复核更正）**：`d5f6eb15` 的缓存键**不是** `stepId+loopIter`，而是 `CallKey(runId, fingerprint, acName, path)`（`PortToolAdapter:49` 记录、`:59-64` 构造），其中 `path = ctx.invocationPath()`，**仅当 path 为空**才回落 `stepId + "|" + loopIter`（`:61-62`）；另有 `discardRunReceipts(runId)`（`:90`）。因此**跨 run 复用不可能**（runId 在键里），「第三次命中缓存」只可能是**同一 run 内同一 invocationPath**；resume 是否重放，取决于该 path 是否重复与 run 结束/取消时是否清账。
- **判据**：补 `farmPort.calls` / 逐次回执 / 缓存清账的精确断言——若「包装器计数 3、真实派发 2」则只是计数口径问题；若「真实派发 3」才是真缺陷。
- **结论（2026-11-22 06:36 实测 trace）**：wrapper1 `port0→1` 回 `harvested=1`；wrapper2 `port1→1` **回同一 1（命中缓存）**；wrapper3 `port1→2` 回 `0`——**3 次包装调用、2 次 fake 端口派发**，第三次没有触发新的底层动作。`AcxFarmContinueOfflineTest` 现为 **3/0/0**。所以这条**不是「重复执行真实动作」缺陷**，是「包装器计数 ≠ 派发计数」。**边界**：仅离线替身证据；缓存清理与真实服务器未验；生产取消语义未改。
